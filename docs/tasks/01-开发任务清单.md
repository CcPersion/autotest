# AI 接口自动化测试平台开发任务清单

> 对应需求：`docs/requirements/01-产品需求规格说明书.md`  
> 任务版本：1.0  
> 更新日期：2026-09-08  
> 状态：当前唯一有效开发任务基线

## 1. 使用规则

本清单共 33 个开发任务，按 5 个阶段交付。每个任务都应产生可运行、可测试的增量，不再建立额外的需求追踪矩阵、任务 DAG 或阶段审查报告。

执行约束：

- 架构设计、数据模型或公共契约的调整使用 Sol 高模型审查。
- 已确认任务的编码、测试和 Bug 修复使用 Luna 极高模型执行。
- 一次只完成一个任务；完成后记录改动、测试命令、结果和遗留问题。
- 开始任务前先运行上一个阶段的门禁；失败时先修复，不绕过测试。
- 默认采用 TDD：先补失败测试，再写最小实现，再运行相关模块测试。
- 未经需求变更，不增加性能压测、RBAC、多 Runner、消息队列、多引擎框架或复杂版本中心。
- 当前仓库不是 Git 仓库，因此任务中的“提交”只表示形成独立可审查改动；初始化 Git 需用户另行授权。

## 2. 当前代码基线

当前仓库已有 Maven 多模块和 Vue 空壳，但仍保留已废弃的纯 Java 执行引擎、复杂快照、租约和 fencing 契约。它们不代表完成的产品功能。

实施时采用以下目标结构：

```text
web                 Vue 页面
platform-api        Spring Boot 平台服务
runner-app          JMeter 转换、执行和结果适配
shared-contracts    平台与 Runner 的少量 DTO
deployment          WSL Docker Compose
```

`engine-core` 在任务 F0-01 中删除。既有源码只保留与新需求相符的最小部分，不能为了兼容旧任务文档继续扩展。

## 4. F0：基线重整

### F0-01 删除旧执行引擎和简化共享契约

- 依赖：无。
- 目标：让代码结构与“自研平台 + JMeter 内核”一致。
- 修改范围：根 `pom.xml`、`engine-core/`、`shared-contracts/`、其他模块 POM 和架构测试。
- 实施内容：删除 `engine-core`；删除 `RunSnapshot` 多选择器、租约、fencing、纯 Java HTTP/SQL/Redis 端口；只保留 `ExecutionPlan`、`RunTask`、`RunEvent`、`StepResult`、`AttachmentRef` 等必要 DTO；更新序列化与架构测试。
- 验收：`mvn test` 通过；仓库中不存在对 `engine-core`、`LeaseDescriptor`、`RunnerWriteEnvelope`、`RootSelector` 的生产引用；共享 DTO 可完成 JSON 往返。

### F0-02 固定 JMeter 5.6.3 Runner 运行环境

- 依赖：F0-01。
- 目标：在 WSL/Docker 中得到可重复的 JMeter CLI 环境。
- 修改范围：`runner-app/pom.xml`、Runner Dockerfile、`deployment/docker-compose.yml`、镜像构建脚本和测试夹具。
- 实施内容：固定 JMeter 5.6.3；下载时校验 SHA-512；使用 Java 17、非 root 用户和独立 `/work/runs`；提供最小 JMX 冒烟计划。
- 验收：容器内 `jmeter --version` 为 5.6.3；`jmeter -n -t smoke.jmx -l result.jtl` 退出码为 0；镜像中不存在 GUI 启动依赖和未审核插件。

### F0-03 整理工程配置与基础门禁

- 依赖：F0-02。
- 目标：形成后续任务共享的构建、格式和测试入口。
- 修改范围：根 POM、`web/package.json`、`.gitignore`、`README.md`、CI 本地脚本。
- 实施内容：统一 Java 17、Spring Boot、JUnit、Vue、TypeScript 版本；排除 `target`、`node_modules`、`dist`、运行目录和密钥文件；提供 Maven、前端类型检查和 Compose 配置检查命令。
- 验收：`mvn test`、`npm.cmd run typecheck`、`npm.cmd run build`、`docker compose config` 全部通过；说明文档为中文。

## 5. F1：最小纵向闭环

### F1-01 建立 Platform API、PostgreSQL 和 Flyway

- 依赖：F0-03。
- 目标：Platform API 可启动并持久化基础数据。
- 修改范围：`platform-api` 启动类、配置、Flyway 迁移、健康检查、Testcontainers 测试。
- 实施内容：接入 PostgreSQL；建立用户、项目、模块、环境、接口定义、接口用例、运行、步骤结果表的第一版结构；实现 `/actuator/health`。
- 验收：空数据库启动自动迁移；重复启动幂等；PostgreSQL Testcontainers 集成测试通过。

### F1-02 实现单用户登录

- 依赖：F1-01。
- 目标：所有平台 API 都受登录保护。
- 修改范围：认证 Controller、Service、Repository、安全配置和登录页面。
- 实施内容：部署变量创建初始管理员；密码强哈希；登录、退出、当前用户、修改密码；失败限流；不实现角色表和权限矩阵。
- 验收：未登录访问业务 API 返回 401；正确登录可访问；错误密码不泄露用户是否存在；端到端登录测试通过。

### F1-03 实现项目与模块管理

- 依赖：F1-02。
- 目标：用户能够建立测试资产目录。
- 修改范围：项目/模块后端接口、数据库仓储、前端项目切换和模块树。
- 实施内容：项目新建、编辑、归档、恢复；模块树新建、改名、排序、移动、删除保护。
- 验收：模块移动后层级和顺序持久化；非空模块不能静默删除；跨项目 ID 访问失败。

### F1-04 实现环境变量和密钥最小能力

- 依赖：F1-03。
- 目标：请求可以使用环境基础地址、普通变量和密钥。
- 修改范围：环境/变量/密钥 API、加密服务、前端环境页和脱敏测试。
- 实施内容：管理 `baseUrl`、普通变量和 `${secret:name}`；主密钥从容器注入；密钥创建后只显示掩码；更新使用 `revision` 防覆盖。
- 验收：数据库中无密钥明文；查询 API 不返回明文；日志扫描不出现测试密钥；环境切换正确。

### F1-05 实现接口定义和接口用例 API

- 依赖：F1-04。
- 目标：保存可执行的 GET/POST JSON 接口用例。
- 修改范围：接口定义/用例领域模型、迁移、REST API、校验和 OpenAPI 文档。
- 实施内容：方法、URL、Path、Query、Header、JSON Body、用例变量、状态码断言、JSONPath 断言；接口定义与用例分离；乐观 revision。
- 验收：创建、读取、更新、归档接口和用例均通过集成测试；非法变量和无效 JSON 返回字段级错误。

### F1-06 实现 Postman 式接口编辑页面

- 依赖：F1-05。
- 目标：用户能在一个页面编辑请求并保存用例，为后续真实调试接入准备完整界面。
- 修改范围：`web/src` 路由、接口列表、请求编辑器、响应面板、提取/断言基本面板。
- 实施内容：模块树 + 列表 + 标签式 Query/Header/Body；环境选择；保存为用例；敏感值掩码；预留由 F1-09 接入的发送和响应区域，不在浏览器实现 HTTP 客户端。
- 验收：组件测试覆盖表格编辑和校验；浏览器可以创建、修改、刷新后重新加载用例；页面不会直连目标服务。

### F1-07 实现基础平台计划到 JMX 的转换器

- 依赖：F1-05、F0-02。
- 目标：把单个 JSON/Query 用例稳定编译成 JMX。
- 修改范围：`runner-app` 中 `JmeterPlanCompiler`、组件映射、金样 JMX 测试。
- 实施内容：生成 Test Plan、单线程 Thread Group、HTTP Request、Header Manager、状态码/JSON 断言；把稳定 `stepId` 写入元素；通过 `SaveService` 保存。
- 验收：转换单测覆盖 GET Query、POST JSON、变量和两类断言；生成文件可由固定 JMeter 真实执行；禁止组件扫描结果为空。

### F1-08 实现单 Runner 数据库队列和 JMeter 子进程

- 依赖：F1-07、F1-01。
- 目标：Runner 能领取、执行、取消和结束一个任务。
- 修改范围：运行 API、任务表、Runner 轮询、工作目录、进程管理和内部认证。
- 实施内容：Platform API 解析并保存执行计划；Runner 原子把一个 `PENDING` 改为 `RUNNING`；生成 JMX；以 CLI 子进程运行；保存退出码；异常产生明确终态。
- 验收：并发两次轮询不能领取同一任务；Runner 进程不因 JMeter 非零退出而退出；重启遗留任务标为 `INTERRUPTED`。

### F1-09 实现基础结果采集和原生报告

- 依赖：F1-08。
- 目标：接通接口页面的“发送”，并看到一次真实请求的完整测试证据。
- 修改范围：平台 JMeter 监听器、JTL 兜底解析、结果回传 API、报告表和报告页面。
- 实施内容：把 F1-06 的发送动作接入运行队列；按 `runId/stepId` 采集请求、响应、耗时、断言和错误；统一脱敏；报告显示运行状态和单步骤详情；大正文截断。
- 验收：成功、断言失败、连接失败三类报告均准确；报告中的密钥被遮蔽；Runner 重复回传不会生成重复步骤。

### F1-10 阶段一端到端验收

- 依赖：F1-01 至 F1-09。
- 目标：证明基础架构不是空壳。
- 修改范围：Playwright、Testcontainers、Compose 验收脚本和中文验收记录。
- 实施内容：启动模拟 HTTP 服务；登录；建项目/环境/用例；运行；查看断言和响应；重启服务后再次查看报告。
- 验收：全新 WSL 执行一条命令启动；核心浏览器流程通过；保存命令、退出码和关键截图；阶段一门禁失败时不得进入 F2。

## 6. F2：完整场景能力

### F2-01 补齐 HTTP、Cookie、证书、代理和文件上传

- 依赖：F1-10。
- 目标：覆盖需求中的全部 HTTP 输入形态。
- 修改范围：平台模型、接口页面、JMeter 转换器、文件/证书存储和集成测试。
- 实施内容：文本、URL Encoded、Multipart、混合文件；Cookie 会话；重定向；超时；代理；PKCS12；最终请求预览。
- 验收：每种 Body 都通过模拟服务校验实际请求；证书和代理有真实集成测试；路径穿越文件名被拒绝。

### F2-02 实现变量、内置函数和运行上下文

- 依赖：F2-01。
- 目标：统一解析所有请求和步骤中的动态值。
- 修改范围：共享执行计划、平台校验、Runner 变量转换和表达式测试。
- 实施内容：`${name}`、`${secret:name}`、UUID、时间戳、日期、随机数/字符串；实现固定优先级和类型保持；不同数据行上下文隔离。
- 验收：优先级表的每一层都有测试；未定义变量运行前失败；密钥不能被普通变量覆盖；并行测试上下文不串值。

### F2-03 实现完整提取与断言

- 依赖：F2-02。
- 目标：覆盖响应、变量、耗时和数据结果校验。
- 修改范围：提取/断言编辑器、校验模型、JMeter 映射、监听器和报告。
- 实施内容：JSONPath、JMESPath、XPath、正则、Header、Cookie；响应状态/正文/JSON/Schema/耗时；多断言全部执行并汇总。
- 验收：提取试算与真实运行一致；同一步两个断言失败时报告显示两个失败；对象和数组提取保持类型。

### F2-04 实现数据行和 CSV 导入导出

- 依赖：F2-02。
- 目标：一个用例使用多组隔离数据顺序执行。
- 修改范围：数据表、CSV 接口、JMeter 数据驱动映射和报告分组。
- 实施内容：页面表格、列校验、CSV 导入预览、导出、启用/禁用行、失败后是否继续下一行。
- 验收：中文、逗号、换行和空值 CSV 往返不丢数据；三行执行产生三个独立报告节点；变量不跨行污染。

### F2-05 实现场景模型和树形编排器

- 依赖：F2-03。
- 目标：按业务流程组合可复用接口用例和自定义步骤。
- 修改范围：场景表/API、步骤 Schema、Vue 树和属性面板、场景校验。
- 实施内容：引用接口用例、复制为独立步骤、自定义 HTTP、排序、嵌套、启停和失败策略；首版拒绝场景引用场景。
- 验收：引用用例更新后新运行使用最新内容，旧运行计划不变；拖拽后顺序持久化；循环引用和非法嵌套在保存/运行前被发现。

### F2-06 实现 JDBC 数据源、SQL 步骤、提取和断言

- 依赖：F2-05。
- 目标：场景可以查询数据库并校验业务结果。
- 修改范围：数据源/密钥 API、SQL 编辑器、JMeter JDBC 映射、PostgreSQL/MySQL 集成测试。
- 实施内容：连接测试；SELECT；参数变量；行列提取；行数/字段/集合断言；写 SQL 分类和二次确认。
- 验收：两个数据库的 Testcontainers 测试通过；未确认写 SQL 不进入任务；报告不显示密码且保留查询摘要。

### F2-07 实现受控 Redis Sampler

- 依赖：F2-05。
- 目标：不使用任意脚本完成 Redis 测试步骤。
- 修改范围：Redis 数据源、平台自研 JMeter 插件、JMX 映射、提取/断言和 Redis Testcontainers。
- 实施内容：GET、SET、DEL、EXISTS；认证、DB 和 TLS 配置；写操作确认；插件白名单和版本校验。
- 验收：四种命令真实执行；插件不能执行 Lua/任意命令；写操作未确认不执行；结果进入原生报告。

### F2-08 实现条件、循环和等待

- 依赖：F2-05。
- 目标：覆盖无脚本的基本业务控制流。
- 修改范围：步骤模型、编排器、条件计算、JMeter If/Loop/ForEach/While/Flow Control 映射。
- 实施内容：变量比较条件、否则分支、固定次数、列表遍历、条件循环、最大循环次数、固定等待。
- 验收：每种控制流有 JMX 金样和真实执行测试；达到最大次数安全停止；禁用分支不产生实际请求。

### F2-09 实现失败策略、重试、取消和独立清理计划

- 依赖：F2-06、F2-07、F2-08。
- 目标：在正常失败与取消时得到可预测的结束行为。
- 修改范围：策略模型、Runner 进程控制、主/清理 JMX、报告汇总和故障测试。
- 实施内容：停止、继续、受控重试；取消先优雅后强制；主流程结束后另启清理计划；分别保存主失败和清理失败。
- 验收：主失败+清理成功、主失败+清理失败、取消+清理、Runner 强杀四类测试通过；强杀场景准确标记清理未执行。

### F2-10 实现测试集合并完成场景门禁

- 依赖：F2-09、F2-04。
- 目标：支持一组用例/场景的顺序回归运行。
- 修改范围：测试集合 API/页面、执行计划解析、集合报告和 Playwright 场景。
- 实施内容：成员选择、排序、环境、启停；运行入口固定为用例/场景/集合；完成“登录→提取→业务→SQL→Redis→清理”验收场景。
- 验收：集合成员和顺序稳定；执行计划中所有引用已解析；业务场景的变量、断言、重试、取消和清理均有报告证据。

## 7. F3：AI 工作台

### F3-01 实现兼容式模型适配和结构化领域工具

- 依赖：F2-10。
- 目标：业务代码不绑定模型厂商，模型不能越权操作平台。
- 修改范围：模型配置、AI 会话、兼容式 Chat API 适配、工具定义、SSE 和测试替身。
- 实施内容：模型地址、模型名、密钥引用；只读资产工具和创建 Patch 工具；超时、重试、取消；模型不可用时不影响手工功能。
- 验收：使用假模型完成工具调用契约测试；模型无法获得数据库/JMeter/文件系统工具；模型密钥不出现在响应和日志中。

### F3-02 实现 Curl 和 OpenAPI 导入

- 依赖：F3-01。
- 目标：把常见输入稳定转换为平台结构，不依赖模型猜测协议细节。
- 修改范围：Curl 解析器、OpenAPI 3 解析器、导入预览和冲突处理。
- 实施内容：Curl 单接口；OpenAPI 批量接口；新增、更新、跳过差异；不自动覆盖已有用例。
- 验收：准备不少于 20 个 Curl 和 3 份 OpenAPI 夹具；解析错误有字段位置；确认前数据库不变。

### F3-03 实现 AI 生成、修改和字段级差异确认

- 依赖：F3-01、F3-02。
- 目标：AI 安全地产生接口、用例和场景草稿。
- 修改范围：Patch Schema、业务校验、差异服务、确认 API 和前端 Diff 组件。
- 实施内容：自然语言生成；对现有草稿增删改；展示旧值/新值、校验错误和危险标记；用户确认后单次事务保存。
- 验收：非法 Patch、陈旧 revision、跨项目引用均被拒绝；关闭确认框不落库；确认后资产内容与预览一致。

### F3-04 实现 AI 首页和失败报告解释

- 依赖：F3-03、F1-09。
- 目标：以 AI 工作台作为首页完成生成和分析流程。
- 修改范围：AI 首页、会话列表、上下文选择、SSE 消息、报告解释工具。
- 实施内容：自然语言/Curl/OpenAPI 输入；生成结果卡片；跳转编辑；读取脱敏失败摘要，输出证据引用和排查建议。
- 验收：Playwright 覆盖“生成→预览→确认→运行→解释”；解释中的步骤和断言能定位到真实报告，不编造不存在的请求。

### F3-05 完成 AI 安全门禁

- 依赖：F3-04。
- 目标：证明云模型不能读取密钥或触发未授权动作。
- 修改范围：脱敏测试、提示注入样本、工具权限测试、模型上下文审计。
- 实施内容：敏感字段替换；上下文截断；恶意 OpenAPI/Curl/响应视为不可信数据；禁止自动运行、通知、写 SQL 和 JMeter 脚本。
- 验收：预设提示注入集全部失败关闭；模型请求抓包不含密钥；任何未确认写操作的执行计数为零。

## 9. 开发过程中的变更规则

出现以下情况时必须暂停当前编码，由 Sol 高模型修改需求并让用户确认，不能由开发任务自行决定：

- 要重新引入自研 HTTP/SQL 执行器；
- 要允许任意脚本或用户插件；
- 要增加多 Runner、性能压测、RBAC、Kafka 或 Kubernetes；
- 要改变接口定义、接口用例、场景三层关系；
- 要把 JMX 变成用户资产或数据库事实源；
- 要增加项目级发布版本或复杂快照中心；
- 要删除需求中列出的 `pytest-auto-api` 核心能力。

普通字段调整、页面细节和 Bug 修复不需要重写需求，只需在当前任务记录中说明并完成相应测试。
