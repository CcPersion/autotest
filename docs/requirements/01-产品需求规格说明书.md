# AI 接口自动化测试平台产品需求规格说明书

> 文档版本：1.0  
> 更新日期：2026-09-08  
> 状态：当前唯一有效需求基线  
> 适用范围：API 功能自动化测试平台，不包含 UI 自动化和性能压测

## 1. 文档目的

本项目从零建设一套团队内部使用的 AI 接口自动化测试平台。平台吸收 `pytest-auto-api` 已验证的测试分层、数据驱动、依赖、提取、断言、SQL/Redis 和清理思想，参考 MeterSphere 的接口调试与场景编排交互，但不复制两者源码，也不以旧 YAML 或 JMX 作为平台的数据模型。

本版采用“自研平台 + Apache JMeter 执行内核”：平台负责资产、交互、AI、安全、调度和报告；JMeter 负责成熟的协议执行与基础控制流。旧版“纯 Java 自研执行引擎”、复杂发布版本、五类运行选择器、多 Runner 租约和 fencing 设计全部失效。

本文件回答“平台要做什么、如何工作、什么算完成”。开发顺序和任务验收见 `docs/tasks/01-开发任务清单.md`。

## 2. 产品目标与边界

### 2.1 产品目标

1. 测试人员不写 Java、Python、pytest 或 JMX，也能通过页面完成接口调试、用例设计、场景编排、执行和报告分析。
2. 保留成熟接口自动化框架的核心思想：接口定义与测试数据分离、公共参数复用、上下游数据依赖、动态提取、多断言、数据驱动、数据库校验和清理。
3. 使用 JMeter 5.6.3 的 HTTP、Cookie、JDBC、提取器、断言、控制器等成熟能力，避免重复实现底层执行器。
4. AI 能通过自然语言、Curl 和 OpenAPI 生成或修改结构化测试资产，但任何变更都必须先展示差异并由用户确认。
5. 在 WSL Docker Compose 中一键部署，形成“创建用例 → 运行 → 查看证据”的完整闭环。

### 2.2 明确不做

- 不复用或调用 `pytest-auto-api` 的 Python/pytest 执行内核。
- 不兼容执行旧 YAML；旧项目只作为功能证据和验收样例来源。
- 不复制 MeterSphere 源码、品牌、页面或受限资源。
- 不让用户直接编辑 JMX；JMX 是 Runner 生成的临时执行文件。
- 首版不做性能压测、分布式压测、UI 自动化、测试管理、缺陷管理或 Mock 平台。
- 首版不做组织、租户、RBAC；登录用户默认拥有平台全部功能。
- 首版只运行一个 Runner 实例，不做租约、fencing、跨节点抢占和 Kubernetes 调度。
- 不允许用户或 AI 执行任意 Python、JavaScript、Groovy、BeanShell、Shell 或操作系统命令。
- 不建设复杂的项目级发布版本和版本中心。

## 3. 产品术语与测试分层

| 名称 | 含义 |
| --- | --- |
| 项目 | 一组接口自动化资产的最高级业务容器。 |
| 模块 | 项目内的树形目录，只负责分类。 |
| 环境 | 基础地址、普通变量、密钥引用和数据源配置的集合。 |
| 接口定义 | 可复用的 API 基础信息，如方法、路径、参数结构和请求体模板。 |
| 接口用例 | 基于接口定义补充输入、变量、断言和数据行后形成的可执行单接口测试。 |
| 场景 | 按顺序编排接口用例、HTTP、SQL、Redis、提取、断言、等待、条件、循环和清理步骤。 |
| 测试集合 | 为回归执行而选择的一组接口用例和场景。 |
| 执行计划 | 某次运行开始前，把引用、环境和数据行解析后保存的结构化 JSON。它是运行证据，不是用户管理的“版本快照”。 |
| Runner | 独立 Java 服务，领取任务、生成 JMX、启动 JMeter、采集结果。 |
| 原生报告 | 平台自己的运行报告；JTL、JMeter 日志和 JMX 只作为运行制品。 |

固定分层为：

```text
项目
  ├─ 模块
  ├─ 环境 / 数据源 / 文件
  ├─ 接口定义
  │    └─ 接口用例 / 数据行
  ├─ 场景
  └─ 测试集合
       └─ 运行记录 / 原生报告
```

## 4. 总体架构

### 4.1 组件

| 组件 | 技术 | 职责 |
| --- | --- | --- |
| `web` | Vue 3 + TypeScript | AI 首页、接口调试、场景编排、配置和报告页面。 |
| `platform-api` | Java 17 + Spring Boot | 登录、测试资产、AI、运行队列、报告、调度和通知 API。 |
| `runner-app` | Java 17 | 解析执行计划、生成 JMX、启动独立 JMeter 进程、取消、清理和结果回传。 |
| `shared-contracts` | Java 17 | 仅保留平台与 Runner 需要共享的执行计划、任务和结果 DTO。 |
| PostgreSQL | 数据库 | 保存用户、测试资产、环境、运行和报告索引。 |
| MinIO | 对象存储 | 保存上传文件、响应附件、临时执行制品和导出报告。 |
| JMeter | 固定为 5.6.3 | 以命令行模式执行 Runner 生成的 JMX。 |

现有 `engine-core` 的纯 Java 自研执行引擎方向废弃。实现阶段删除该模块，将必要的 JMeter 编译和结果适配代码放入 `runner-app`，不额外创建通用“多引擎插件框架”。

### 4.2 运行数据流

```text
用户点击运行
  → Platform API 校验并解析环境、引用和数据行
  → 保存本次执行计划 JSON，创建待执行任务
  → 单 Runner 原子领取任务
  → 在独立运行目录生成 JMX 和临时密钥文件
  → 启动 jmeter -n 子进程
  → 受控监听器输出结构化步骤事件
  → Runner 回传步骤、断言、日志和附件
  → Platform API 汇总原生报告
  → 清理临时密钥和运行目录
```

每个 JMeter 运行在独立子进程中。JMeter 异常或插件崩溃不能导致 Runner 主进程退出。

### 4.3 平台数据与 JMeter 的边界

- 平台数据库中的结构化资产是唯一编辑事实源。
- 平台步骤必须使用稳定 `stepId`；生成 JMX 时写入测试元素，报告再用它关联页面步骤。
- JMX、JTL 和 JMeter 日志按运行生成，不反向覆盖平台资产。
- JMeter 版本固定，升级必须重新执行转换契约测试和参考案例。
- JMeter 程序化构建接口集中在 Runner 内部；不得让该依赖扩散到 Platform API 和 Web。

## 5. 用户与核心流程

### 5.1 用户模型

首版只有“登录用户”一种身份。登录后可以管理所有项目、密钥、执行、AI 和系统配置。系统仍记录创建人、修改人、运行人和时间，供审计与问题定位使用。

### 5.2 核心流程一：调试并保存接口用例

1. 用户选择项目、模块和环境。
2. 新建接口定义，填写方法、URL、Query、Header、Cookie 和 Body。
3. 点击“发送”进行临时调试。
4. 从响应中添加提取规则和断言，或由 AI 建议规则。
5. 保存为接口用例，可继续增加多组数据行。
6. 点击运行，在报告中查看请求、响应、提取值和断言结果。

### 5.3 核心流程二：编排业务场景

1. 创建场景。
2. 从接口列表引用已有接口用例，或添加临时 HTTP 步骤。
3. 添加 SQL、Redis、等待、条件、循环和清理步骤。
4. 使用前序步骤输出作为后续请求输入。
5. 校验场景，解决缺失变量、循环引用和危险操作问题。
6. 选择环境和数据行运行，查看场景树报告。

### 5.4 核心流程三：AI 生成后人工确认

1. 用户在 AI 工作台输入自然语言、Curl 或 OpenAPI。
2. AI 读取当前项目允许的结构化上下文。
3. AI 返回新增或修改建议，不直接保存。
4. 页面展示字段级差异、校验错误和危险提示。
5. 用户确认后保存草稿，再手动运行。

## 6. 功能需求

### 6.1 登录与项目

- 使用用户名和密码登录，支持退出和查询当前用户。
- 初始管理员由部署环境变量创建，首次登录后可以修改密码。
- 密码必须使用强哈希保存，连续失败需要短时限流。
- 项目支持新建、编辑、归档和恢复；已有运行记录的项目不得物理删除。
- 模块支持任意层级树、排序和移动；删除非空模块前必须明确提示。
- 所有资产操作限定在当前项目内。

### 6.2 环境、变量和密钥

环境包含：

- `baseUrl`；
- 普通变量，支持字符串、数字、布尔值和 JSON；
- 密钥引用；
- 默认请求头；
- HTTP 代理、重定向和超时；
- PKCS12 客户端证书引用；
- JDBC 数据源引用；
- Redis 数据源引用。

密钥要求：

- 密钥值加密保存，主密钥从容器环境注入。
- 页面创建后只显示掩码，不提供明文回显接口。
- AI、日志、报告、通知、JMX 和命令行不得出现密钥明文。
- Runner 仅在执行前把所需密钥写入权限受限的临时文件，运行结束立即删除。

### 6.3 接口定义与调试

接口定义支持：

- HTTP 方法：GET、POST、PUT、PATCH、DELETE、HEAD、OPTIONS；
- URL 的环境基础地址、固定地址和 Path 参数；
- Query、Header、Cookie；
- Body：none、JSON、纯文本、`x-www-form-urlencoded`、`multipart/form-data`；
- 单文件、多文件和文本字段混合上传；
- 请求超时、代理、是否跟随重定向、Cookie 会话、PKCS12 证书；
- Curl 导入、OpenAPI 导入与导出 Curl；
- 发送前预览最终 URL、Header 和 Body，密钥只显示掩码。

调试请求也必须由 Runner/JMeter 执行，保证“调试成功”和“自动化运行”的底层行为一致。调试结果可以一键保存为接口定义或接口用例。

### 6.4 接口用例与数据驱动

- 一个接口定义可以创建多个接口用例。
- 用例可覆盖接口定义的参数值、请求头、请求体和超时，但不能改变所属接口。
- 用例包含用例变量、前置步骤、请求、提取、断言和清理步骤。
- 数据表第一行定义列名，其余行为数据；支持页面编辑、CSV 导入和 CSV 导出。
- 默认按数据行顺序串行执行；单行失败是否继续下一行由用例配置决定。
- 用例可以独立运行，也可以被场景引用。
- 引用是默认复用方式：接口用例修改后，场景下次运行使用最新保存内容；本次运行仍以已经保存的执行计划为准。
- 用户可以选择“复制为独立步骤”，复制后不再随源用例变化。

### 6.5 场景编排与复用

场景编辑器使用树形步骤编排，支持拖拽排序、启用/禁用、复制、删除、折叠和搜索。支持以下步骤：

| 步骤 | 能力 |
| --- | --- |
| 引用接口用例 | 复用已有接口用例及其提取、断言。 |
| HTTP | 在场景内直接定义一次性请求。 |
| SQL | 执行查询；写 SQL 必须二次确认。 |
| Redis | GET、SET、DEL、EXISTS；写操作必须二次确认。 |
| 提取 | 从响应体、响应头、Cookie、SQL 或 Redis 结果产生变量。 |
| 断言 | 对响应、变量、SQL 结果或耗时进行校验。 |
| 等待 | 固定毫秒等待。 |
| 条件 | 条件成立时执行子步骤，支持否则分支。 |
| 循环 | 固定次数、遍历列表和条件循环；必须设置最大次数。 |
| 清理 | 主流程结束后执行，默认即使主流程失败也尝试执行。 |

首版不支持场景引用另一个完整场景，避免递归与循环依赖。公共登录、造数等复用通过“接口用例引用”实现；确有需要时再增加受控的公共步骤组。

### 6.6 变量与表达式

统一表达式使用 `${name}`，内置函数使用 `{{$function}}`。首版内置 UUID、当前时间戳、格式化日期、随机整数和随机字符串。

变量优先级从高到低固定为：

```text
前序步骤提取值 > 当前数据行 > 接口用例变量 > 场景变量 > 环境变量
```

- 场景运行前必须检查未定义变量。
- 变量可以用于 URL、Query、Path、Header、Cookie、Body、SQL、Redis 参数和断言期望值。
- 变量保留原始类型；只有目标字段要求文本时才转成字符串。
- 密钥使用 `${secret:name}`，不能被提取、覆盖或写入普通变量。
- 单个运行上下文隔离，不同运行和不同数据行不得互相污染。

### 6.7 提取

支持以下提取方式：

- JSONPath；
- JMESPath；
- XPath；
- 正则表达式；
- 响应头；
- Cookie；
- HTTP 状态码；
- SQL 结果的行列；
- Redis 返回值。

提取规则包含来源、表达式、变量名、默认值和“未命中是否失败”。页面提供基于当前响应的即时试算。数组和对象保持 JSON 类型，不强制序列化为文本。

### 6.8 断言

支持：

- HTTP 状态码；
- 响应头、Cookie；
- 响应正文等于、包含、不包含、正则匹配；
- JSONPath/JMESPath 的存在、不存在、等于、不等于、大于、小于、包含；
- JSON Schema；
- 响应时间上限；
- 普通变量比较；
- SQL 查询结果的行数、字段值和集合包含；
- Redis 返回值比较。

同一步骤可以配置多个断言。必须执行完该步骤的全部断言再汇总结果，报告同时展示所有失败断言，不因第一个失败而隐藏后续问题。

### 6.9 SQL 和 Redis

- JDBC 数据源首版支持 PostgreSQL、MySQL；其他数据库通过增加驱动和兼容测试扩展。
- SQL 查询结果可提取和断言。
- 默认只允许 SELECT。INSERT、UPDATE、DELETE、DDL 和存储过程必须在步骤上标记“允许写入”，运行前再次确认。
- Redis 数据源支持认证、数据库编号和 TLS 配置。
- Redis 通过审核过的受控 JMeter 插件实现，不允许用户输入任意 Lua 脚本。
- 数据源密码遵循密钥规则。

### 6.10 失败策略、重试、取消和清理

普通步骤支持三种失败策略：

1. 停止主流程；
2. 记录失败并继续；
3. 重试当前步骤后停止或继续。

重试配置包含最大次数、固定间隔和仅针对连接错误/超时/指定状态码。默认不重试有副作用的请求，用户明确开启才允许。

清理步骤与主步骤分组显示，并遵守以下规则：

- 主流程成功、失败或用户取消后，都应尝试执行清理。
- 多个清理步骤按配置顺序执行，一个清理失败不阻止其余清理。
- 清理失败单独展示，不能覆盖主流程原始失败原因。
- 若 Runner 或宿主机被强制终止，无法保证清理执行；报告必须明确标记“清理未执行”，不得伪装成功。

取消运行时，Runner 先请求 JMeter 优雅停止；超过配置时间后终止子进程，然后启动独立清理计划。

### 6.11 测试集合、运行与队列

- 测试集合按顺序包含多个接口用例或场景，可选择环境。
- 运行入口只有三种：接口用例、场景、测试集合。
- Platform API 在事务中解析所有引用并保存一份执行计划 JSON，然后才把任务置为待执行。
- 执行计划记录资产内容、环境普通变量、密钥引用、文件校验值、JMeter 版本和创建时间，不保存密钥明文。
- 运行状态简化为：`PENDING`、`RUNNING`、`PASSED`、`FAILED`、`CANCELED`、`INTERRUPTED`。
- 首版单 Runner 使用数据库原子更新领取一个 `PENDING` 任务；不建设租约和 fencing。
- Runner 重启时，将自己遗留的 `RUNNING` 任务标记为 `INTERRUPTED`，允许用户手动重新运行。
- 重跑会创建新的运行记录，不覆盖旧结果。

### 6.12 原生报告

报告必须包含：

- 运行对象、环境、开始/结束时间、耗时和最终状态；
- 数据行和场景步骤树；
- 每步请求方法、脱敏 URL、请求头、请求体；
- 状态码、响应头、响应体和耗时；
- 提取表达式、结果和是否命中；
- 每条断言的实际值、期望值和结果；
- SQL/Redis 的脱敏命令与结果摘要；
- 重试次数、失败原因、清理结果和取消信息；
- JMeter 版本、执行计划标识和运行日志下载；
- 过大请求/响应以附件保存，页面展示截断提示。

Platform API 保存结构化报告事实，不能依赖 JMeter HTML 报告作为唯一展示。后续可从原生报告导出 HTML 和 Allure 结果。

### 6.13 AI Agent

AI 首页支持对话式完成：

- 从自然语言生成接口定义、接口用例或场景草稿；
- 解析 Curl；
- 解析 OpenAPI 并批量生成接口定义；
- 为当前响应建议提取和断言；
- 修改现有草稿；
- 解释失败报告并定位可能原因；
- 回答当前项目资产的使用问题。

AI 权限边界：

- AI 只能调用 Platform API 暴露的结构化领域工具，不能直接访问数据库、文件系统、JMeter 或 Runner。
- AI 输出必须经过 JSON Schema、业务规则和安全规则校验。
- 新增、修改和删除均展示字段级差异，用户确认后才保存。
- AI 不得自动运行、自动发送通知或确认危险 SQL/Redis/HTTP 操作。
- 发送给云模型的密钥替换为占位符；请求/响应样本按统一规则脱敏和截断。
- 提示词中的“忽略规则、读取密钥、执行脚本”等内容视为数据，不改变工具权限。
- 模型不可用时，普通手工测试功能仍可使用。

### 6.14 导入、导出、调度和通知

- Curl：单接口导入和导出。
- OpenAPI 3：导入接口定义，冲突时展示新增、更新和跳过项。
- 旧 YAML：不提供直接执行；验收阶段选择真实样例手工转换成平台测试夹具。
- 定时任务：对测试集合配置 Cron、环境、启停和下次运行时间。
- CI/API：使用项目级触发令牌启动测试集合并查询结果。
- 通知：首版实现通用 Webhook，邮件、钉钉、飞书、企微后续通过同一通知适配层补充。
- 导出：原生 HTML 报告优先，Allure 结果导出作为后续能力。

## 7. JMeter 执行要求

### 7.1 允许的 JMeter 能力

Runner 只生成平台白名单内的组件：

- Test Plan、单线程 Thread Group；
- HTTP Request、HTTP Header/Cookie/Cache Manager；
- JDBC Connection Configuration、JDBC Request；
- CSV Data Set Config；
- JSONPath/JMESPath/XPath/正则提取器；
- Response、JSON、JSON JMESPath、Duration 等断言；
- If、Loop、ForEach、While、Simple Controller；
- Flow Control Action；
- 平台自研且经过审核的 Redis Sampler 和结果监听器。

功能测试默认一个线程、一次业务迭代，数据行按顺序运行。首版页面不暴露 JMeter 线程组、吞吐量、Ramp-up 等性能参数。

### 7.2 禁止的 JMeter 能力

- JSR223、BeanShell、BSF、OS Process、任意 Java Request；
- 用户上传的 Jar 或 JMeter 插件；
- 未在白名单内的 Sampler、PreProcessor、PostProcessor 和 Listener；
- 在命令行参数、JMX 或 JTL 中写入密钥明文；
- 使用 GUI 模式执行服务器任务。

### 7.3 转换与结果契约

- `runner-app` 中建立“平台步骤 → JMeter 组件”的明确映射表。
- 编译器使用固定 JMeter 依赖构建 `HashTree`，通过 `SaveService` 写出 JMX。
- 为每种步骤保留最小金样 JMX，升级 JMeter 时做结构对比和真实执行回归。
- 平台监听器以 JSON Lines 输出步骤开始、结束、断言、错误和附件索引。
- JTL 和日志解析是兜底；原生报告不得只依赖脆弱的控制台文本解析。

## 9. REST 与实时事件

- API 统一以 `/api/v1` 开头，使用 JSON；文件上传和下载除外。
- 资源包括：认证、项目、模块、环境、密钥、数据源、文件、接口、用例、场景、测试集合、运行、报告、AI、调度和通知。
- 更新请求携带 `revision`，用于防止两个页面互相覆盖；它不是产品发布版本。
- AI 流式回复和运行进度使用 SSE。
- Runner 使用内部接口领取任务、上报事件和完成结果，并通过部署密钥认证。
- 创建运行和 Runner 结果回传使用幂等键，防止网络重试产生重复记录。
- 错误响应统一包含 `code`、`message`、`details` 和 `traceId`。

## 10. 安全要求

- 请求目标默认受项目级域名/IP 白名单限制；允许配置内网目标，但必须显式加入。
- 阻止通过重定向绕过白名单，并重新校验最终目标。
- 文件限制类型、大小和数量；文件名不能决定服务器路径。
- 日志和报告统一调用脱敏组件，默认遮蔽 Authorization、Cookie、密码、令牌和用户配置的敏感字段。
- 任何写 SQL、Redis 写操作和被标记为危险的 HTTP 请求必须有显式确认记录。
- Runner 容器使用非 root 用户、只读基础文件系统和独立临时运行目录；仅授予测试目标所需网络。
- JMeter 及第三方依赖锁定版本并执行依赖漏洞扫描。
- 登录、密钥修改、危险确认、运行、取消和通知记录审计日志。

## 11. 非功能要求

### 11.1 性能与容量

- 首版支持 20 名内部用户、100 个项目、10 万条运行步骤历史。
- 普通列表 API 在 5 万条索引数据下 P95 小于 1 秒。
- 创建运行到 Runner 开始处理在空闲状态下小于 5 秒。
- 单次请求/响应正文默认展示上限 1 MB，超出部分进入附件；单运行附件默认上限 100 MB。
- 单 Runner 同时只执行一个 JMeter 任务，避免资源争用；并发执行在后续阶段评估。

### 11.2 可靠性

- PostgreSQL 是状态事实源，MinIO 是文件事实源。
- Platform API 或 Web 重启不能丢失已保存资产和报告。
- Runner/JMeter 异常必须产生明确的 `INTERRUPTED` 或 `FAILED`，不能永久停留在运行中。
- 数据库和对象存储提供备份、恢复说明和一次真实恢复演练。

### 11.3 可观测性

- 所有服务提供健康检查。
- 日志包含 `traceId`、`runId`、`stepId`，不得包含密钥。
- 系统设置页显示 Runner 在线状态、JMeter 版本、队列长度和最近心跳。
- 保存 JMeter 退出码和截断后的错误日志，便于定位转换或执行问题。

### 11.4 可维护性

- 后端和前端字段由 OpenAPI 契约保持一致。
- 数据库使用 Flyway 迁移，不手工修改部署数据库。
- JMeter 转换器、结果适配器和安全校验分别测试，不混成单个大类。
- 所有说明性文档使用中文。

## 12. 部署要求

WSL Docker Compose 最终包含：

```text
web
platform-api
runner-app（镜像内固定 JMeter 5.6.3）
postgresql
minio
```

- 平台不依赖 Kafka、平台 Redis、Kubernetes 和远程 JMeter 集群。
- 首次启动自动迁移数据库并创建管理员。
- 容器提供健康检查、持久卷和示例环境文件。
- JMeter Runner 镜像构建时校验发行包 SHA-512，不使用 nightly build。
- `docker compose up -d` 后必须能通过浏览器完成核心闭环。

## 13. 验收标准

### 13.1 第一阶段闭环

在全新 WSL 环境中，可以登录、新建项目和环境、创建一个 JSON 接口用例、通过独立 JMeter 运行并在原生报告中看到请求、响应和断言。重启 Compose 后数据仍存在。

### 13.2 核心功能闭环

可以编排“登录 → 提取 token → 业务请求 → JDBC 校验 → Redis 校验 → 清理”的场景；变量传递、多个断言、失败策略、重试、取消和清理结果均有报告证据。

### 13.3 AI 闭环

可以从自然语言、Curl 和 OpenAPI 生成结构化草稿；页面显示差异；未经确认数据库不变；确认后可以运行；云模型输入和日志中不存在密钥明文。

### 13.4 参考框架能力闭环

从真实 `pytest-auto-api` 中挑选至少以下测试夹具，手工转换为平台资产并通过执行：

1. GET + Query + 缓存变量；
2. POST JSON + 多断言；
3. 多接口依赖和 JSONPath 提取；
4. 多数据行；
5. SQL 断言；
6. Redis 读写；
7. 文件上传；
8. 动态 UUID/时间/随机数据；
9. 前置造数和失败后清理；
10. 通知和报告导出。

每个夹具必须能指向：参考 YAML/源码证据、平台页面配置、生成的 JMX、运行结果和原生报告。只要仍有确认能力未覆盖，就不能宣称“1:1 功能复刻完成”。

### 13.5 安全闭环

至少验证：密钥不回显、日志脱敏、SSRF 重定向绕过失败、危险 SQL 未确认不执行、恶意文件名无法越界、AI 提示注入不能调用未授权工具、JSR223/BeanShell/OS Process 无法进入 JMX。

## 14. 分阶段范围

### 阶段一：可运行基础闭环

登录、项目/模块、环境变量、JSON/Query 接口用例、状态码/JSON 断言、JMeter 子进程、基础原生报告、Compose。

### 阶段二：完整接口与场景能力

全部请求体、Cookie/TLS/代理、文件、数据行、场景编排、变量提取、SQL、Redis、失败策略、重试、取消和清理。

### 阶段三：AI 工作台

自然语言/Curl/OpenAPI 生成、差异确认、失败解释、模型配置和安全校验。

### 阶段四：运营与最终验收

测试集合、Cron、CI/API、Webhook、HTML/Allure 导出、审计、备份恢复、参考框架夹具和安全验收。

阶段是交付顺序，不代表后续能力可以永久删除；但任何阶段不得提前引入分布式执行、性能压测或复杂版本系统。

## 15. 设计依据

- Apache JMeter 官方说明其可用于功能行为测试，并提供 HTTP、JDBC、断言、提取器、控制器及 CLI 执行能力。
